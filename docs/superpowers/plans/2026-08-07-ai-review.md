# AI Review Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the all-or-nothing AI preview modal with a per-change review — inline decorations in the note, a rail carrying each change's model-authored reason, and approve/deny per suggestion.

**Architecture:** The server owns a 56-check catalogue grouped into 8 families and serves it over HTTP, so the client never holds a second copy that can drift. A suggestion run fans out one model request per enabled family in parallel and returns a flat `AiEdit[]`, each edit anchored to a block by its existing TipTap `UniqueID` and carrying a required `reason`. The client renders those as ProseMirror decorations — the document is not mutated until an approval is dispatched, and each approval remaps the remaining pending edits through `tr.mapping`.

**Tech Stack:** TypeScript, Express (server), Vitest (server tests), React + TipTap/ProseMirror (web), Playwright (e2e), oxlint.

## Global Constraints

- **Never touch `web/index.html`.** It carries a sha256-pinned inline script whose hash is duplicated in `vercel.json` and `server/src/lib/csp.ts`. Editing it — even a comment — silently breaks CSP in production.
- **`web` has no unit test runner.** Do not add one. Web changes are verified by `npm run build -w web` (this is the typecheck: `tsc -b && vite build`), `npm run lint -w web` (oxlint), and Playwright specs via `npm run e2e`.
- **Server tests are Vitest:** `npm test` from the repo root, specs in `server/test/*.test.ts`.
- **An `AiEdit` with an empty `reason` is invalid.** Reject it server-side. A rail card with no reason renders blank and the feature's whole premise collapses.
- **Never fabricate a model response in shipped code.** Where a backend does not yet exist, the control is rendered disabled with an honest reason. No stubs, no placeholder toasts.
- Match the surrounding code's comment density — this codebase writes substantial "why" comments on non-obvious decisions.
- Commit after each task. Do not push. Do not open PRs.

### Revision to Task 5, found during build

`POST /api/ai/gaps` **already existed** before this plan was written — it powers the
Assistant panel and returns advisory markdown ("Missing from your notes" / "Worth
double-checking"), documented in `docs/API.md`. The plan was wrong to specify it as new.

Two agents found this independently and reached the same conclusion: the new route is
`POST /api/ai/gaps/edits`, sitting **alongside** the original rather than replacing it.
The two answer different questions — one produces prose a human reads, the other
produces applicable `AiEdit[]`. Collapsing them would have broken the Assistant panel.

### Carry into Task 9

`CheckPicker` currently defaults to the catalogue's **first preset by position** when a
notebook has no saved selection. That means reordering `PRESETS` in
`server/src/lib/checks.ts` silently changes what every new user gets — a server-side
cosmetic edit changing client behaviour is a trap. Replace it with an explicit default:
either a `default: true` flag on one `Preset` in the catalogue, or the client naming
`'lecture-notes'` by id. Naming the id is not "hardcoding" in the bad sense; it is
stating an intent that positional indexing only implies.

The rest of the picker's storage design is right and should be kept: `null` ("never
chosen") and `[]` ("deliberately turned everything off") are stored distinctly, so
turning every family off survives a reload instead of silently reverting to the default.

### Task 3: The `AiEdit` contract and its validator

**Files:**
- Create: `server/src/lib/aiEdit.ts`
- Test: `server/test/aiEdit.test.ts`

**Interfaces:**
- Consumes: `checkById` from Task 1
- Produces:
```ts
export interface AiEdit {
  id: string;
  blockId: string;
  op: 'replace' | 'insert' | 'delete';
  before: string;
  after: string;
  reason: string;
  checkId: string;
  source?: { attachmentId: string; label: string };
}

/** Drops anything the model returned that we refuse to render. */
export function validateEdits(raw: unknown): { edits: AiEdit[]; rejected: number };
```

Rejection rules — each exists because rendering the alternative is worse than dropping
the suggestion:

| Rejected when | Why |
| --- | --- |
| `reason` missing or blank after trim | the rail card would render empty |
| `checkId` not in the catalogue | can't assign a severity, so can't sort the rail |
| `blockId` missing or blank | nothing to anchor to |
| `op: 'replace' \| 'delete'` with blank `before` | nothing to match against the document |
| `op: 'insert' \| 'replace'` with blank `after` | approving it would do nothing |

- [ ] **Step 1: Write the failing test**

```ts
// server/test/aiEdit.test.ts
import { describe, it, expect } from 'vitest';
import { validateEdits } from '../src/lib/aiEdit';

const ok = {
  id: 'e1', blockId: 'b1', op: 'replace',
  before: 'a queue', after: 'a FIFO queue',
  reason: 'Your notes distinguish FIFO from priority queues.',
  checkId: 'clarity.two-names-one-thing',
};

describe('validateEdits', () => {
  it('keeps a well-formed edit', () => {
    const r = validateEdits([ok]);
    expect(r.edits).toHaveLength(1);
    expect(r.rejected).toBe(0);
  });

  it('rejects an edit with no reason', () => {
    const r = validateEdits([{ ...ok, reason: '   ' }]);
    expect(r.edits).toHaveLength(0);
    expect(r.rejected).toBe(1);
  });

  it('rejects an unknown checkId', () => {
    expect(validateEdits([{ ...ok, checkId: 'made.up' }]).edits).toHaveLength(0);
  });

  it('rejects a replace with nothing to match on', () => {
    expect(validateEdits([{ ...ok, before: '' }]).edits).toHaveLength(0);
  });

  it('rejects an insert that inserts nothing', () => {
    expect(validateEdits([{ ...ok, op: 'insert', before: '', after: '' }]).edits).toHaveLength(0);
  });

  it('survives junk without throwing', () => {
    expect(validateEdits(null).edits).toEqual([]);
    expect(validateEdits([1, 'x', {}]).rejected).toBe(3);
  });
});
```

### Task 4: Family-scoped suggestion route

**Files:**
- Modify: `server/src/routes/ai.ts`
- Test: `server/test/aiSuggest.test.ts`

**Interfaces:**
- Consumes: `FAMILIES` (Task 1), `validateEdits` (Task 3)
- Produces: `POST /api/ai/suggest` with body `{ noteId: string; families: string[] }`
  → `{ edits: AiEdit[]; rejected: number; ranFamilies: string[] }`

**One model request per enabled family, issued in parallel.** Six to eight related
checks per prompt is inside what a model reads carefully; 56 checks in one prompt gets
shallow coverage of all 56. This is the single most important thing about this route.

The note is serialised for the prompt as blocks tagged with their `UniqueID`, and the
model is instructed to echo the id back in each edit.

A family whose request fails must not fail the whole run — collect what succeeded,
and report which families actually ran in `ranFamilies` so the client can say so.

Quota: price the run by **number of families**, not one call. Read
`server/test/aiQuota.test.ts` and the existing quota helper before writing this, and
follow whatever it already does — do not invent a second quota mechanism.

**Interfaces:**

- Produces: `POST /api/ai/gaps` with body `{ noteId: string }` → same shape as Task 4

Compares the note against its own `note.attachments` — the photo, slides and

**Every edit this route returns must have `op: 'insert'`.** It adds what the source

Every edit must carry `source: { attachmentId, label }`, where `label` is human-facing
and specific: `"slide 14 of 31"`, `"24:10–28:35"`. A citation the user cannot act on is
worse than none.

`"Import slides, a photo or a transcript first."`

### Task 6: The review plugin

**Files:**
- Create: `web/src/features/editor/AiReviewPlugin.ts`
- Modify: `web/src/features/editor/NotePage.tsx` (register in `handleEditorReady`)

**Interfaces:**
- Consumes: the `AiEdit` shape from Task 3 (redeclare it in `web/src/lib/types.ts` — the
  workspaces do not share types today, and this plan does not change that)
- Produces:
```ts
export const AiReviewPluginKey: PluginKey<AiReviewState>;

export interface AiReviewState {
  pending: AiEdit[];
  settled: Record<string, 'approved' | 'denied'>;
  stale: string[];          // ids whose block vanished or whose `before` no longer matches
}

export function createAiReviewPlugin(): Plugin;

// Commands dispatched via editor.view.dispatch:
export function setReviewEdits(view: EditorView, edits: AiEdit[]): void;
export function approveEdit(view: EditorView, editId: string): void;
export function denyEdit(view: EditorView, editId: string): void;
export function clearReview(view: EditorView): void;
```

Register it in `handleEditorReady` beside the existing two, using the same
double-registration guard — React 18 StrictMode mounts twice:

```ts
if (!AiReviewPluginKey.get(editor.state)) {
  editor.registerPlugin(createAiReviewPlugin());
}
```

Four things this must get right:

1. **Decorations only.** The document is not mutated until `approveEdit`. Inline
   decoration for insertions (underlined), inline for deletions (struck through, text
   left in place). Autosave must never observe a half-reviewed document.
2. **Resolve `blockId` → position on every apply, not once up front.** Walk the doc for
   the node whose `id` attr matches. Positions from a previous state are stale.
3. **Remap after every approval.** Replacing four words with two shifts everything
   after it. Map surviving pending edits through `tr.mapping` in `apply()`. **This is
   the most likely route to a corrupted note in the whole feature.**
4. **Mark stale, don't silently drop.** If the block is gone, or its text no longer
   contains `before`, move the edit's id into `stale`. The rail reports the count.

Notation blocks (chem, model3d, sketch) cannot render a strikethrough — decorate the
whole node instead and let the rail card carry the before/after.

### Task 7: The review rail

**Files:**
- Create: `web/src/features/editor/AiReviewRail.tsx`
- Create: styles in `web/src/features/editor/aiReview.css`

**Interfaces:**
- Consumes: `AiReviewState` and the command functions from Task 6; family severity from
  `GET /api/ai/checks` (Task 2)
- Produces: `<AiReviewRail editor={editor} onDone={() => void} />`

Cards grouped by **severity**, not document order — severity comes from the edit's
check family. This is what stops "this contradicts your Dijkstra note" being buried
under six capitalisation fixes.

Each card: category chip, block reference, the reason, Approve / Deny. Cards with a
`source` additionally render the citation line. Footer: Approve all, Discard.

Volume control, since 56 checks on a long note can produce 40 suggestions: collapse
families, cap the cards rendered per family, and where capped say so explicitly —
`"12 more in Grammar"`. **Never silently truncate.**

Stale edits render as a single dismissible line — `"2 suggestions no longer apply"` —
not as cards.
